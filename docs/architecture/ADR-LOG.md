## ADR-0001 — طبقة `ComputerProvider` مستقلة عن المزودين
- **الحالة:** Accepted (D4)
- **السياق:** المزودون (Browserbase, E2B, Vercel Sandbox, ذاتي الاستضافة) يختلفون في الإمكانيات (سطح مكتب، إيقاف/استئناف، بث، حدود الجلسة) والتسعير، وقد تتغير شروطهم. المعيار المعتمد: عدم الارتباط بمزود واحد.
- **القرار:** عقد موحد `ComputerProvider` مع `capabilities` معلنة (انظر الخطة §6.3). لا يظهر كائن مزوّد خارج الـ adapter. كل adapter يجتاز **contract tests** مشتركة قبل التفعيل. `act()` يقبل `ActionGrant` فقط.
- **العواقب:** + استبدال/إضافة مزود بجهد محدود، ومقارنة عادلة في Phase 0. − كلفة تصميم أولية، وخطر «أصغر قاسم مشترك» (يُخفَّف بالـ capabilities الاختيارية).
- **البدائل المرفوضة:** استدعاء SDK المزود مباشرة من الوكيل (ارتباط ثقيل)؛ تجريد كامل يخفي الفروق (يضيع ميزات مثل Contexts/Pause).
- **يُراجَع عند:** إضافة مزود لا يلائم العقد (مثلًا Windows).

<a id="adr-0002"></a>
## ADR-0002 — Browser Mode أول منتج قابل للتشغيل
- **الحالة:** Accepted (D1)
- **السياق:** مهام المالك الأساسية (Daftra، مواقع إدارية، حسابات) تعمل في المتصفح. المتصفح أرخص وأسرع وأيسر أمنيًا، ويتيح قراءة DOM/شجرة الوصول إلى جانب الرؤية.
- **القرار:** Phase 1–3 تبني المتصفح فقط؛ Desktop يأتي في Phase 4 كوضع منفصل بسياسات منفصلة.
- **العواقب:** + أقصر طريق لقيمة تشغيلية؛ + تقليل سطح الهجوم. − مهام تتطلب تطبيقات مكتبية مؤجلة.
- **البدائل المرفوضة:** سطح مكتب لكل المهام (أغلى وأوسع هجومًا).
- **يُراجَع عند:** ظهور مهام أساسية لا تُنجز بمتصفح.

<a id="adr-0003"></a>
## ADR-0003 — مقارنة Browserbase وE2B عمليًا قبل الالتزام
- **الحالة:** Accepted (D2)
- **السياق:** الوثائق لا تجيب عن: لوحة مفاتيح iPhone، الكتابة العربية، رابط البث وحدود أمانه، حظر الشبكة الداخلية، تسجيلات تكشف حقولًا حساسة، وزمن/تكلفة فعليين.
- **القرار:** Phase 0 يشغّل PoC متطابقًا على المزودين (PV/IP/AR/SEC)، بمعايير **إقصاء** إلزامية ثم تقييم موزون (iPhone 25%، الأمان/العزل 20%، الاستمرارية 15%، التكلفة 15%، الدمج 10%، العربية 10%، التحكم الحي 5%). لا التزام إنتاجي قبل تقرير Phase 0.
- **العواقب:** + قرار مبني على قياس. − 1.5–2 أسبوع قبل البناء.
- **البدائل المرفوضة:** الاختيار بالوثائق والتسعير فقط.
- **يُراجَع عند:** تغيّر جوهري في شروط المزودين قبل الإنتاج.

## ADR-0004 — Linux Desktop لاحقًا؛ Windows Provider محجوز بلا تنفيذ
- **الحالة:** Accepted (D3) · Windows: **Deferred**
- **السياق:** `docs/ARCHITECTURE.md` الأصلي افترض Windows سحابيًا؛ المزودون المقارَنون يوفرون Linux. أدوات مثل `windows.run_action` وتكامل `windows_worker` معرّفة بحالة `planned`.
- **القرار:** Desktop المستقبلي على Linux (Phase 4). `capabilities.modes` يحتفظ بالقيمة `desktop-windows` كنقطة امتداد، **دون** بحث أو تنفيذ أو عمل على Windows الآن. يبقى `windows_worker` في الكتالوج بحالة `planned`، وتُعاد تسمية الأدوات إلى `computer.*` عند التنفيذ (قرار لاحق).
- **العواقب:** + لا تعقيد ترخيص Windows الآن؛ + مسار مفتوح لاحقًا. − برامج Windows الحصرية غير مدعومة حتى قرار جديد.
- **البدائل المرفوضة:** البدء بـ Windows (أغلى، ترخيص، تشغيل غير مراقب غير محسوم).
- **يُراجَع عند:** ظهور حاجة فعلية لبرنامج Windows حصري.

## ADR-0005 — Worker مستقل للمهام الطويلة
- **الحالة:** Accepted (D5)
- **السياق:** حلقة الوكيل تمتد دقائق وتحتاج حالة وlease؛ الـ API على Vercel serverless بمدد محدودة وبلا ضمان استمرار.
- **القرار:** خدمة Worker دائمة (container) تملك المهمة ودورتها، تتصل بـ PostgreSQL مباشرة بدور `safwan_worker` المقيَّد، وتُنبَّه من الـ API بطلب موقَّع (انظر ADR-0011). العميل مراقب فقط.
- **العواقب:** + انقطاع العميل لا يؤثر؛ + استعادة ممكنة. − خدمة إضافية للنشر والمراقبة وتكلفة ≈ $13/شهر ❓.
- **البدائل المرفوضة:** حلقة داخل API (حدود المدة)؛ طابور خارجي مُدار قبل الحاجة.
- **يُراجَع عند:** حاجة لتوسع يتجاوز عملية واحدة بشكل ملحوظ.

## ADR-0006 — إعادة استخدام PostgreSQL والمصادقة من PR #26 بعد التحقق
- **الحالة:** Accepted (D6)
- **السياق:** PR #26 يوفر RLS ودورًا مقيّدًا وجلسات وتوقيع BFF→API بمراجعة وثّقها. لم يُثبت على Preview/Neon، وهو غير مدموج، ولا يتضمن تسجيل دخول (B2).
- **القرار:** لا بناء فوقه قبل اجتياز بوابة G1–G10 (الخطة §3.3) وصدور تقرير تحقق موافَق عليه. لا دمج بدونه. جداول الكمبيوتر تتبع نفس نمط RLS/الأدوار.
- **العواقب:** + لا أساس ثانٍ؛ + أمان مراجَع. − اعتماد على B2 وعلى نجاح التحقق.
- **البدائل المرفوضة:** أساس بيانات جديد؛ بناء فوق PR غير متحقق منه.
- **يُراجَع عند:** فشل G3/G6/G7 بما لا يُعالج بتغيير صغير.

## ADR-0007 — الأمان قبل القدرة: Policy Gate والموافقات قبل الإجراءات المؤثرة
- **الحالة:** Accepted (revision M1)
- **السياق:** `execute_tool` الحالي يُرجع `approval_required` بلا قناة اعتماد. الوكيل بدون Gate قادر نظريًا على إرسال/حذف/دفع.
- **القرار:**
  1. Policy Gate حتمي (تصنيف R0…E2/U من ملاحظات قابلة للتحقق، بعقد مشترك ومتجهات اختبار) + قناة موافقات (استهلاك أحادي، `action_hash`، انتهاء، Step-up) تُبنى في **Phase 1**.
  2. `computer.effects` علم مطفأ افتراضيًا؛ الوكيل قراءة فقط حتى تنجح **Effects Gate** (EG1–EG9).
  3. الإنفاذ بطبقتين: أداة الوكيل بلا مقبض مزود، و`act()` يرفض بلا `ActionGrant` صالح.
  4. النموذج لا يعتمد عملياته ولا يعدّل تصنيفها.
- **العواقب:** + لا مسار لتجاوز السياسة بالتعليمات. − Phase 1 أثقل، والإجراءات المؤثرة تتأخر لما بعد Phase 2.
- **البدائل المرفوضة:** سياسة في الـ prompt؛ موافقات تُبنى بعد الوكيل.
- **يُراجَع عند:** فشل أي EG لا يُعالج؛ لا يُخفَّف الشرط.

<a id="adr-0008"></a>
## ADR-0008 — Effect Journal وRecovery
- **الحالة:** Accepted (revision M2)
- **السياق:** انقطاع Worker/اتصال أثناء إجراء مؤثر قد يترك النتيجة مجهولة؛ إعادة المحاولة العمياء قد تكرر فاتورة/إرسالًا/دفعًا.
- **القرار:** كتابة النية قبل الإرسال (`action_intents`، `idempotency_key`)، معاملة واحدة لاستهلاك الموافقة + الانتقال إلى `dispatching` + فحص `lease_epoch` (fencing)، وحالات `outcome_unknown/verifying/needs_human`. التمييز: R0/R1 آمنة؛ R2 آمنة بعد إعادة التحقق من الحالة؛ E1 تحقق ثم أعد؛ **E2 لا إعادة تلقائية، تحقق للقراءة فقط وموافقة جديدة قبل أي إعادة**. علامة تحقق قابلة للبحث ضمن كل إجراء E2.
- **العواقب:** + ضمانة at-most-once للمؤثر. − بعض الحالات تنتهي بتدخل بشري (مقبول). − تعقيد آلة الحالات واختباراتها (EG5).
- **البدائل المرفوضة:** إعادة محاولة تلقائية شاملة؛ ادعاء exactly-once.
- **يُراجَع عند:** دعم نظام هدف لمفاتيح idempotency أصلية (يُستفاد منها).

## ADR-0009 — iPhone Safari شرط قبول
- **الحالة:** Accepted (revision M4)
- **السياق:** الجوال هو الجهاز الأساسي؛ وثائق Browserbase تذكر أن لوحات المفاتيح المحمولة غير مدعومة رسميًا في Live View؛ باقي المزودين غير محقق.
- **القرار:** IP1–IP9 (مشاهدة، كتابة إنجليزية وعربية، تحكم يدوي، تسليم/استلام، استعادة اتصال، موافقة، تخطيط، أمان الرابط) على جهاز iPhone حقيقي (Safari وPWA) **معيار إقصاء** للمزوّد وشرط إطلاق. الكتابة عبر شريط إدخال أصلي لا عبر لوحة داخل iframe.
- **العواقب:** + لا مفاجأة متأخرة. − اعتماد على جهاز حقيقي ووقت اختبار.
- **البدائل المرفوضة:** اختبار على محاكيات فقط؛ تأجيل iPhone لما بعد MVP.
- **يُراجَع عند:** تغيّر سلوك iOS/Safari يكسر بندًا.

## ADR-0010 — حوكمة التكلفة: ميزانيات وإيقاف تلقائي
- **الحالة:** Accepted (revision M5)
- **السياق:** النموذج يمثل > 95% من تكلفة المهمة (≈ $0.45–0.70 لنموذجية بـ Sonnet 5.5 ❓ تقدير)؛ حدود $5/يوم و$40/شهر قررها المالك في `DECISIONS.md` (PR #26).
- **القرار:** `BudgetMeter` في الخادم: حجز مسبق ذرّي قبل كل نداء، وتصحيح بالاستهلاك الفعلي، ودفتر `usage_ledger` بالميكرو-دولار. سقف المهمة الافتراضي **$1.00** (تحذير 70%، طلب موافقة تمديد 90%، إيقاف 100% مع بقاء Context)، يومي $5، شهري $40، ثم سقوف خطوات (80) ومدة (60د) وخمول (10د) وكشف عدم التقدم. النموذج لا يستطيع تجاوزها.
- **العواقب:** + لا فاتورة مفاجئة. − مهام ثقيلة تتطلب تمديدًا صريحًا؛ سقف $40 يكفي ≈ 57–89 مهمة نموذجية.
- **البدائل المرفوضة:** مراقبة بعد الوقوع؛ حدود من لوحة المزود فقط.
- **يُراجَع عند:** قياس Phase 0 للتكلفة الفعلية، أو تغير أسعار النماذج.

<a id="adr-0011"></a>
## ADR-0011 — PostgreSQL طابورًا مع wake-up بدل الاستقصاء
- **الحالة:** Proposed
- **السياق:** الاستقصاء الدوري يبقي Neon مستيقظًا (≈ $19/شهر لـ 0.25 CU دائمة ❓) بدل ≈ $0–4 مع autosuspend. RLS يمنع اكتشاف الوظائف عبر الحسابات دون آلية.
- **القرار:** `worker_claim_job()` دالة `SECURITY DEFINER` محصَّنة (`pg_temp` أخيرًا، أسماء مؤهلة) بـ `FOR UPDATE SKIP LOCKED` ودور `safwan_worker` غير مالك؛ تنبيه موقَّع من الـ API (`/wake`)؛ الـ Worker الخامل لا يفتح اتصالًا؛ نبض كل 15ث أثناء الـ leases؛ فحص احتياطي كل 10د. لا Redis في v1.
- **العواقب:** + تكلفة وبساطة. − منطق wake-up إضافي؛ فقد wake يُغطّى بالفحص الاحتياطي.
- **البدائل المرفوضة:** Redis/Kafka قبل الحاجة؛ استقصاء ثابت؛ `BYPASSRLS` للـ Worker.
- **يُراجَع عند:** رصد زمن وصول طابور غير مقبول، أو تجاوز عملية واحدة.

## ADR-0012 — بيانات الاعتماد لا تصل النموذج
- **الحالة:** Proposed
- **القرار:** تسجيل الدخول للمواقع بالتحكم اليدوي مرة واحدة ثم Context/Profile محفوظ عند المزود؛ أسرار أخرى بمرجع `{{secret:name}}` يحقنه الخادم داخل الـ adapter؛ الحقول الحساسة لا تُلتقط في أحداث ولا لقطات ولا تُمرَّر للنموذج؛ فحص أن تسجيلات المزود لا تكشفها (SEC-04) وإلا تُعطَّل.
- **العواقب:** + تقليل أثر الحقن والتسرب. − تدخل يدوي عند انتهاء الجلسة، وعدم دعم مواقع بلا Context.
- **البدائل المرفوضة:** تمرير كلمات المرور عبر الـ prompt؛ تخزينها في سجلات.

## ADR-0013 — مسار المشاهدة الحي المصادَق (V1/V2/V3)
- **الحالة:** Proposed
- **السياق:** رابط Live View (Browserbase) قد يتيح المشاهدة والتحكم لمن يحمله (bearer)؛ وثائقه لا تغطي حماية الرابط. فحص الملكية قبل إصدار الرابط لا يمنع نسخه واستخدامه من متصفح غير مصادَق خلال عمره.
- **القرار:** لا يُسلَّم الرابط الخام للعميل إلا في **V1** بعد إثبات (PV-13/IP-09 على الرابط **النهائي**) أنه مرتبط بجلسة/عميل مصادَق. وإلا: **V2** Viewer Gateway يتحقق من جلستنا عند كل اتصال ويُبقي الرابط الخام داخل الخادم، أو **V3** عارض خاص (لقطات/screencast عبر قناتنا المصادَقة والتحكم عبر `/input` والـ Gate). `GET /computer/jobs/{id}/live` يخدم الرابط المصادَق/التذكرة فقط. CSP `frame-src` لنطاق البث المعتمد.
- **العواقب:** + لا وصول بنسخ الرابط. − V2/V3 يضيفان مكوّنًا وزمنًا، وجدواهما ❓ تُقاس في Phase 0.
- **البدائل المرفوضة:** تسليم رابط bearer بعد فحص ملكية فقط.

<a id="adr-0014"></a>
## ADR-0014 — تخزين الكائنات خلف `StorageAdapter`
- **الحالة:** Proposed
- **القرار:** واجهة تخزين خاص (مفتاح `account/job/...`، TTL، روابط موقعة قصيرة). الافتراضي المقترح Cloudflare R2 (≈ $0.015/GB-شهر، egress مجاني، 10GB مجانًا)؛ Vercel Blob مقبول للـ MVP. اللقطات TTL 7 أيام.
- **العواقب:** + تكلفة ≈ $0 وقابلية الاستبدال. − حساب/مزود إضافي إن اختير R2.
- **يُراجَع عند:** قرار خطة Vercel أو سياسة احتفاظ مختلفة.

<a id="adr-0015"></a>
## ADR-0015 — النموذج الافتراضي للوكيل
- **الحالة:** Proposed (يُحسم بقياس Phase 0 ثم Phase 2)
- **القرار المؤقت:** Sonnet 5.5 افتراضيًا (≈ $0.44–0.68 LLM لمهمة 30 خطوة)؛ مقارنة Haiku 5.5 (أرخص بنحو 20×، جودة غير مُثبتة) وOpus 5.5 (أعلى جودة محتملة، ≈ 1.6×–1.8×) على نفس المهام. قواعد تقنية: أداة `computer_toolset_20260801`، تفكير تكيفي، بلا `tool_choice` إجباري (يُرفض على Sonnet 5.5)، تفعيل prompt caching وتقليم اللقطات، ومعالجة `stop_reason: refusal` وfallback حسب إرشادات المنصة.
- **معيار القرار:** نسبة نجاح مهام PoC، التكلفة/مهمة، الالتزام بالنطاق تحت الحقن.

<a id="adr-0016"></a>
## ADR-0016 — إنفاذ الشبكة على مستوى الطلب
- **الحالة:** Proposed
- **السياق:** مرشح URL على الإجراءات المقترحة لا يغطي تحويلات 30x ولا الموارد الفرعية ولا `fetch/XHR/WebSocket` من صفحة مسموحة ولا الأسماء التي تُحل إلى عناوين خاصة أو تتبدّل (rebinding)؛ فلا يصلح تعويضًا عن غياب حجب الشبكة.
- **القرار:** يشترط إنفاذ الحجب لكل طلب يصدره المتصفح، بعد حل الاسم إلى IP، للنطاقات الخاصة وlink-local وloopback وMetadata (IPv4/IPv6 وتمثيلاتها)، بإحدى طريقتين: سياسة egress يفرضها المزوّد وتُثبت بمصفوفة SEC-01 كاملة، أو وكيل egress ترشيحي نملكه تمر به كل حركة المتصفح. مرشح URL في الـ Gate **دفاع إضافي** ولا يُحتسب في الإقصاء. `egress_control` في `ProviderCapabilities` يُملأ بنتيجة الاختبار لا بإعلان المزوّد.
- **العواقب:** + سد مسار SSRF الحقيقي. − قد يُقصي مزودًا أو يتطلب وكيلًا (تكلفة وصيانة، ودعم المزود لوكيل مخصص ❓).
- **يُراجَع عند:** تغيّر سياسات المزود أو ظهور مسار طلب لا تغطيه المصفوفة.
