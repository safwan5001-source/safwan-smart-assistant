## 1. Purpose and current baseline
The owner performed real iPhone testing using Safari, Chrome and the installed PWA. The objective is to make BASHT the primary owner interface to the existing agent, without duplicating the agent or rebuilding working features. Preserve the approved BASHT identity and current operational capabilities.

Evidence classification (owner screenshots/reports, not a fresh source-code audit):
- Passed on device: owner sign-in; display of distinct browser sessions; text replies; Markdown headings, lists and tables; switching between two Claude models with retained conversational context; sending and analyzing an image; receiving, previewing and downloading a previously generated image; receiving/downloading an XLSX through a direct attachment route; speech input converted to text; displaying real scheduled tasks and their execution history; displaying capabilities, memory files and Arabic memory search; test push notification outside app and in-app test notification with unread badge; light/dark rendering; visual 3D HQ.
- Defects/limitations observed: durable display of sent image after response reconciliation; voice reply not audible despite a speaking state; attachment delivery reported failures before alternate route succeeded; chat search did not retrieve recent matching app messages; new chat currently creates a context boundary in a single timeline rather than independently resumable threads; certain scheduled jobs ran but did not achieve their business objective because required tools were unavailable; some status indicators conflict with working features.
- Blocked: new image generation returned provider 429 according to the agent; GPT model switching deferred because owner reported usage limit exhausted. Do not infer provider billing reason from 429 alone.
- Unverified or incomplete: actual voice output, full-duplex realtime, document upload to agent, persistent image history across reload, in-app file save and pinch zoom, real per-model reasoning effort, multi-browser live synchronization, end-to-end approval/denial and expiry, actual event-driven push and notification deep links, remote session revocation, complete export, task mutation and settings persistence. A visible control is not proof of its backend behavior.
- No functional failure inferred merely from a read-only feature or an explicitly deferred feature.

## 2. Architecture and boundaries
- Application: `safwan5001-source/safwan-smart-assistant` (web/PWA, API, PostgreSQL). Engine: `safwan5001-source/openclaw-railway-template` (OpenClaw). Verify actual stack, current main heads, deployment and contract before planning. Keep two repositories; no merge or third repository.
- Engine owns agent execution, model routing, sessions, shared memory, authorized tools, channel and scheduler integrations. App owns presentation, authentication, app records and secure mediation. Define a single source of truth for each entity.
- Extend the existing narrow authenticated bridge through reviewed, least-privilege, versioned contracts; preserve owner access, channel/session isolation, existing WhatsApp operation and safe fallbacks. No arbitrary engine proxy or broad access.
- Railway is the deployment platform; Vercel is not production. No new services, paid providers, infrastructure migration or public endpoint expansion without approval.
- Previous integrated release: engine PR #57, app PR #66, their feature PRs closed after integration. Verify main and live deployed versions rather than reimplementing them. Engine #50 (WhatsApp audio documents STT) and #51 (Yemeni voice guidance) remain independent; do not merge or close them under this roadmap.
- Scope: A stability, B chat, C control center, D shared design/performance, E separate visual HQ, F validation. A/B are highest user priorities; sequence according to verified dependencies, not arbitrary parallel edits.

## 3. A — Stability and correctness (first delivery focus)
### A01 — Audio reliability
Observed: speech converted to text and agent text reply received; no audible voice response on the tested iPhone even when UI said speaking. Diagnose exact cause; distinguish browser dictation from engine STT, engine TTS, audio transport and Safari/PWA playback. Inspect current browser voice integration and reuse it where supported, rather than assuming a new API or subscription is necessary. Verify provider auth and capability discovery without reading/exposing secrets. Preserve current approved BASHT voice, pronunciation and dialect settings; do not change providers or modify the separate voice skill.
- Fix Listen action under replies, audio recording, transcript, actual audio response and playable voice messages. Support recording/upload/download as appropriate and visible progress, stop, retry, permission-denied and unavailable states.
- Support continuous hands-free sequential turns, auto-resume listening after response, interruption and stop, where supported. Distinguish sequential STT/chat/TTS from genuine realtime full-duplex; do not label one as the other. Plan real realtime separately if the existing integration cannot provide it. No silent fallback that claims voice success.
- Only report listening/thinking/speaking when corresponding activity is real. Handle media permissions, autoplay restrictions, interruptions, focus, route changes, disconnection and quota without stuck UI. Verify actual audible output and latency on iPhone.
### A02 — Voice experience
Full-screen mobile voice UI instead of narrow side drawer. Official BASHT character centered, restrained wave animation driven by real state, controls for mic/mute, speaker, stop/interrupt/end and optional transcript. Retain conversation context and show turns in chat. Short tap on central BASHT bottom navigation opens text chat; long press opens live voice experience (subject to permission); avoid accidental click, double activation and browser context menu; accessible equivalent, optional haptic feedback only where supported. Do not auto-record outside explicit interaction.
### A03 — Attachment lifecycle
Fix optimistic message versus server reconciliation so sent images remain visible after reply, refresh, reopening and authorized cross-device access. Persist structured attachment metadata and stable authorized references, not internal filesystem paths as user-visible text. Maintain original chat records; redact technical paths at presentation boundary without corrupting runtime references.
- Diagnose direct attachment versus failed delivery tool path; provide reliable in-chat attachments. Inbound and outbound documents (PDF/XLSX/DOCX/text), images, audio/video where supported; explicit unsupported states. Use actual file contents rather than claim success from a filename.
- Upload/download progress, limits, validation, error/retry, display friendly complete filename/type/size; avoid unnecessary duplicates. Preserve image compression and metadata privacy as applicable. Verify received spreadsheets open and calculate; no assumption that generating an XLSX proves its contents or cached values.
- Keep authenticated media routes and no-store protections; prevent access after logout/revocation and ensure old clients remain safe. Define retention, cleanup and storage limits; no bulk deletion.
### A04 — Media viewer and generation
Full-screen neutral dark viewer; aspect fit, pinch zoom/pan, close, concise display filename, download, save to library, OS share where supported; accessible alternatives. Documents: preview where supported, fallback open/download; not just a server path.
- Image generation provider 429: diagnose quota/rate/credit using authorized evidence; display clear availability and retry/backoff; no repeated paid calls or automatic top-up. Test delivery with existing authorized fixture without generation cost.
### A05 — Tool availability and scheduled execution
Compare actual effective tools for owner app, authorized owner channel, engine main and scheduled sessions. Installed skill, ready skill, enabled plugin, available tool and successful tool execution are distinct. Investigate missing search/browser and authorized accounting integration in relevant sessions; do not grant unrestricted tools or expand channel scope. Preserve accounting read-only/write approval constraints.
- Investigate paused heartbeat inference-account binding and failed accounting report tool availability; do not reactivate or send production reports without approval.
- Separate transport/runtime success, objective completion and delivery. A report saying required research could not be performed is blocked/partial, not successful objective. Use structured result contract with evidence and status. Do not invent evidence or infer absence of opportunities from lack of tools.
### A06 — Authoritative status
Correct misleading provider, authentication, voice, service/version and connection status. Separate legacy direct provider integration from engine-mediated provider, app authentication from synchronization, configured from reachable and tested. Explicit unknown/degraded states. Do not equate missing direct API key with unavailable subscription-backed engine. Avoid exposing account identifiers, raw sensitive logs or internal paths in ordinary UI.

## 4. B — Chat experience and data architecture
### B01 — Mobile chat redesign
Reference: owner-provided Claude iPhone screenshots. Use interaction patterns, not copied branding. Preserve BASHT purple/gold and official character. One minimal header with chat navigation and status; remove nested heavy panel/header and repeated explanatory text (move to info). Maximize width for assistant replies and tables; distinct user bubbles. Preserve Markdown, tables, links, code, copy, Listen, stop/retry actions.
- Composer at bottom, multiline auto-growing, stable above keyboard/safe areas, sends/stops appropriately; compact plus button and model-name/effort chip, mic and voice controls. Expanded composer when typing. Plus opens mobile bottom sheet: photos, camera, files, execution mode/permissions, search/research, integrations, skills, memory, only if actually available. No inert toggles or fake capabilities. Model chip opens separate picker. Bottom nav remains functional, including BASHT long press. No permanent second tool toolbar above content.
- Ensure latest messages button does not obscure report content; preserve scroll position, accessible jump-to-latest, live streaming without jitter; tables scroll horizontally within available width. Support mixed RTL/LTR and readable numeric columns. Preserve drafts/attachments across navigation and retry.
### B02 — Independent conversations
Implement real independently resumable threads, not just timeline separators. Fresh empty screen, auto-generated/editable titles, list by date, open/resume, pin, archive, search; per-thread model, supported effort and attachments. Share approved long-term BASHT memory without leaking transient context between threads or other contacts. Existing owner app history must remain accessible and safely migrated; distinguish app sessions from browser auth sessions. Define thread-to-engine-session mapping, bridge validation, isolation and fallback; no broad arbitrary session IDs. Plan additive backwards-compatible schema/contract migration, preservation checks, rollback and recovery before implementation. Do not delete old history or alter WhatsApp session mappings.
### B03 — Search and synchronization
Server-backed search across authorized app threads and history. Arabic diacritics-insensitive normalization, mixed language, ranking, highlight, clean snippets without raw Markdown, open exact message, filters by source/date/type. Authorized owner-channel history stays read-only and separately identified; no other DMs/groups. Memory and file search separate or explicitly filtered. Investigate existing missing recent results, indexing freshness and pagination.
- Synchronize chats, messages, attachments, read state and relevant app data across authenticated devices/browsers. Establish canonical IDs, deterministic ordering, idempotency, race handling, offline/reconnect, deduplication and state recovery. Verify two-browser same-thread and different-thread cases, concurrent sends and new-thread operations; no lost/duplicated responses. Preserve local data until migration verified.
### B04 — Model picker, effort and usage
Compact grouped provider list in bottom sheet, current selected model and actual executed model, fallback clearly disclosed; curated frequently used models and more models list, default engine option preserved. Only advertise capabilities, context sizes, effort and fast mode verified from runtime/provider; do not duplicate translated effort labels or show unsupported settings. Show model availability and known limits, unknown otherwise. Do not change WhatsApp/global model by changing app chat. Preserve context on supported switch.
- Separate usage page: per-thread and all-agent day/month usage, context and latency, transparent scope and data freshness. Distinguish token counts, API-equivalent estimate, actual billed cost and subscription usage; mark partial/unknown without inventing totals. Do not assume displayed dollars are charges. No expensive retries while quota exhausted.

Reduce redundant headings, cards, gradients, shadows and whitespace; unified icons, typography, spacing, density, controls, bottom sheets, dialogs and states. No fabricated metrics. More is a compact grouped menu with clear access to files, reminders, notifications, voice, integrations, memory and settings; avoid duplicate headings and oversized cards.

Test installed PWA, Safari and Chrome, narrow viewport, rotation, keyboard and safe areas; review service worker/update lifecycle and private caching. No regression of existing authenticated media no-store and logout protection.
