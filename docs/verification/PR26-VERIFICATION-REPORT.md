## 3. جاهزيته أساسًا للكمبيوتر السحابي (Worker وجداول جديدة)

| الموضوع | الخلاصة |
|---|---|
| جدول جديد مملوك لحساب | `account_id` أولًا في PK وكل فهرس، `ENABLE`+`FORCE`، سياسة واحدة `FOR ALL TO safwan_app` بـ USING وWITH CHECK، منح دنيا؛ للجداول الأبناء مفتاح أجنبي مركّب `(account_id, parent_id)` لأن فحص FK يتجاوز RLS (وإلا مرجع عابر للحسابات ووسيلة سؤال عن الوجود) |
| حجز الوظائف عبر الحسابات دون BYPASSRLS | دور `safwan_worker` منفصل بسياسته الضيقة (أو دالة `SECURITY DEFINER` لكن **بحذر:** على جدول FORCE وبمالك غير superuser قد ترى الدالة صفرًا من الصفوف في Postgres العادي بينما ترى الكل على Neon/superuser — **سلوك يختلف بين CI وNeon**، فيُختبر بمالك غير superuser). الدالة: `FOR UPDATE SKIP LOCKED`، `search_path = pg_catalog, pg_temp` فقط، REVOKE من PUBLIC، تُرجع معرّفات فقط |
| النطاق داخل المعالجة | `owner_transaction` ترفض nil/غير المحدد (صحيح)، فالحجز يكون بسياسة دور لا بنطاق؛ ثم كل وظيفة داخل `owner_transaction(account_id)` **بلا تداخل** (F3) |
| صلاحيات افتراضية | لا `ALTER DEFAULT PRIVILEGES` في 0001: أي دالة جديدة قابلة للتنفيذ من PUBLIC ما لم تُسحب صراحة |
| الخدمة-إلى-خدمة | للـ Worker سر/سياق مستقل (F9)؛ وعميل BFF يحتاج بثًا (مهلة 3ث وسقف 64KB حاليًا) |
